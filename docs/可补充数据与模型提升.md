# 沟通：还有什么数据可以帮助模型分析比赛

本文档基于当前预测引擎已用数据，列出**尚未充分使用或尚未接入**、且对分析/预测有帮助的数据方向，便于产品与开发对齐。

---

## 一、当前模型已在用的数据

| 类型 | 来源 | 用途 |
|------|------|------|
| 主/客近期比分 | matches | 主主场、客客场近期场均进/失 → 期望进球 |
| 历史交锋 | matches | 主客直接对话 → 与近期期望进球按比例融合 |
| 积分榜排名 | league_standings | 主客队当季排名 → 期望进球微调 |
| 胜平负赔率 | match_odds | 与模型概率线性融合 |
| 伤停 | match_injury | 缺阵人数/关键球员 → 期望进球下调 |
| 休息天数 | matches | 距上场比赛天数 → 疲劳系数 |
| API-Football 预测 | api_football_predictions | 第三方预测概率融合 |
| 主场优势 | 配置 | 主队期望进球乘数 |
| 概率校准 / ML 修正 | calibration_params, outcome_ml | 胜平负概率后处理 |

**赔率数据说明**：胜平负赔率来自 API-FOOTBALL 的 Odds 接口（或竞彩 API）。**API-FOOTBALL 官方文档**（[Odds 端点](https://www.api-football.com/documentation-v3#tag/Odds-(Pre-Match)/operation/get-odds)）约定：Pre-match 赔率仅在赛前 **1～14 天** 提供，且只保留 **7 天历史**，因此无法用该接口拉取数月/整年的历史赔率。免费档还可能在「可用赛季」上受限；若 dashboard 报「赔率端点不存在」需在后台开通 Odds。

**长期历史赔率可选来源**（API-FOOTBALL Odds 不能提供长期历史时）：

| 来源 | 说明 | 项目现状 |
|------|------|----------|
| **体彩网 + 体彩 API** | 体彩场次/赛果 + 固定奖金接口（如 `getFixedBonusV1.qry`），按日期拉取后可长期落库 | 已设计并部分实现（见 [竞彩方案设计.md](竞彩方案设计.md)）；体彩数据按日积累即形成历史，可与 `match_odds`（source=sporttery）打通 |
| **第三方竞彩 API** | 按日期/场次拉胜平负、让球等 | 已支持配置（`JC_ODDS_*`、`etl/jc_odds_api.py`）；是否提供长期历史取决于服务商文档 |
| **国际盘口历史 API** | 专做历史赔率的付费服务，覆盖多年、多联赛 | 项目未集成；可选服务示例：[The Odds API Historical](https://the-odds-api.com/historical-odds-data)（2020 年起）、[OddsMatrix](https://oddsmatrix.com/products/historical-odds/)、[TxODDS](https://txodds.com/)、[BetsAPI](https://betsapi.com/docs/events/)（2016 年起）等，需单独对接与付费 |

结论：若要做**长期历史赔率**（如 2024 全年、多赛季），优先用**体彩网 + 体彩 API** 按日拉取并落库；需要国际盘口多年历史时可评估上述第三方历史 Odds API 并接入。

### 完善赔率实操步骤（体彩 → match_odds）

1. **按日拉取体彩赔率并写入 DB**  
   - 单日：`python main.py sporttery-odds-to-db --date 2024-12-26`  
   - 日期范围：`python main.py sporttery-odds-to-db --dates 2024-01-01,2024-12-31`  
   - 最近 N 天：`python main.py sporttery-odds-to-db --days 30`  
   - 数据会写入 `match_odds`，`source=sporttery`，含胜平负及让球等扩展字段；仅处理五大联赛。  

   **注意**：体彩网接口（webapi.sporttery.cn 等）经实测**仅对「当天」或近期日期有数据**，历史日期（如 2024-01-01）多返回空或非 JSON。要做长期历史赔率只能**每天跑一次** `sporttery-odds-to-db --date 当天` 做积累，或改用支持历史查询的第三方竞彩 API。

2. **（可选）队名规范化与关联 matches**  
   - 体彩多为中文队名，若要与 `matches` 关联以便预测/复盘用上赔率，执行：  
     `python main.py normalize-team-names` → `python main.py link-match-odds`  
   - 查看统计：`python main.py odds-stats`；查看无赔率场次：`python main.py list-matches-without-odds`。

3. **近期 7 天内可补 API-FOOTBALL**  
   - API-FOOTBALL Odds 仅保留 7 天历史，若已开通 Odds，可对「今天或过去 7 天」补拉：  
     `python main.py odds-api-by-db --limit 7 --rate-limit 0.05`  
   - 与体彩赔率并存，预测时按场次取可用来源即可。

4. **第三方竞彩 API**  
   - 若已配置 `JC_ODDS_API_BASE`、`JC_ODDS_API_TOKEN`，可直接用命令按日期范围写入历史赔率：  
     `python main.py jc-odds-to-db --dates 2024-01-01,2024-12-31`（或 `--date YYYY-MM-DD`、`--days N`）。  
   - 数据写入 `match_odds`，`source=jc_api`；默认仅五大联赛，加 `--no-five-only` 可写入全部联赛。是否支持历史日期取决于服务商文档。

## 二、可补充、对分析有帮助的数据

**API-Football 专项**：项目已用与尚未接入的接口、以及对模型预测的用途与优先级，见 [API-Football可拉取数据与预测用途.md](API-Football可拉取数据与预测用途.md)。



### 1. 已具备数据源、尚未深度参与预测

| 数据 | 现状 | 可做之事 | 难度 |
|------|------|----------|------|
| **xG（预期进球）** | 配置有 `PREDICT_USE_XG`、`PREDICT_XG_BLEND`，默认关闭；API-Football statistics 有射门/射正可近似 xG | 用近期场均 xG（或射正/射门比）与当前「形式期望进球」混合，减少偶然大胜/大败的干扰 | 低：已有接口与混合逻辑，需把 statistics 按场次关联并算近期均值后传入 `predict_match` |
| **单场统计（射门、控球、角球等）** | `statistics-api` 写入 `data/api_football_statistics.json`，文档注明「未落 DB」「可用于复盘或后续特征」 | 主/客近期场均射门、控球率、角球等 → 作为风格/压制力特征（如控球高且射门多的队倾向多进球）；或仅用于复盘/报告 | 中：需按 team+日期聚合近期统计，并设计入参与公式（如对期望进球的轻量调整） |

### 2. 需新拉取或新加工的数据

| 数据 | 说明 | 对分析的价值 | 难度 |
|------|------|--------------|------|
| **裁判** | 主裁判历史出牌、点球倾向等 | 对「平局」「小比分」或红牌/点球敏感场次有参考 | 中高：需新数据源或 API 字段 + 规则/特征设计 |
| **赛程密度 / 连续客场** | 未来 N 天比赛场次、是否连续客场 | 与现有「休息天数」互补，刻画一周双赛、连续奔波 | 中：基于现有赛程即可算，需定义「密度」指标并接入预测 |
| **赛季阶段 / 动机** | 轮次、与保级/争冠/欧战线的分差 | 保级队主场、争冠关键战等动机不同，可能影响战意 | 中：积分榜与赛程已有，需定义「动机」标签或分数 |
| **近期实际进球 vs xG** | 近期场均进球 − 近期场均 xG（或射正相关近似） | 把握机会能力 / 运气：实际高于 xG 可能回调，低于 xG 可能反弹 | 低中：依赖 xG 或近似 xG 的接入 |
| **半场/领先被追平历史** | 半场领先却未赢、补时被追平等 | 心理或风格（是否易被翻盘）的粗特征 | 中：需从比分与半场比分算统计，再作特征 |
| **阵容/阵型或首发稳定性** | 换帅、阵型变化、主力轮换比例 | 稳定性高更易用历史表现推断 | 高：依赖更细的阵容或新闻数据 |
| **上场人员名单** | 首发 XI（及可选替补），API-Football `fixtures/lineups` 可拉 | 与伤停结合：识别「关键球员缺阵」更准，参与现有伤停下调；可选做轮换/首发稳定性特征（相对上轮变动） | 中：需落库完整阵容（球员 ID/姓名）、关键球员名单或历史阵容用于对比；当前仅展示用「上场人数」不参与模型 |
| **转会/身价/薪资** | 球队总身价、夏窗净投入等 | 长期实力与赛季预期，对「冷门」有参考 | 高：需新数据源与更新频率定义 |
| **天气 / 场地** | 雨雪、场地类型等 | 对部分联赛/场地类型可能影响比分与风格 | 中高：需新数据源 |

### 3. 仅用于「展示/解读」、不参与模型

| 数据 | 说明 |
|------|------|
| 更细伤停（位置、预计复出时间） | 已有 impact 高/中/低，可展示更细文案，模型侧可维持当前按人数/关键球员的规则 |
| 历史相同对阵在不同赛事 | 已有历史交锋，可区分联赛/杯赛展示，模型可选按赛事过滤或加权 |

## 三、全量命中率 70% 与数据/特征的关系

- **现状**：规则 + ML + 校准一起上时，头部联赛约 56%～65%，全量到 70% 仅靠调参很难达到。  
- **结论**：冲 70% 需要**更多特征或更多数据**（见下节优先级）；同时产品上可用「高置信度子集」「按联赛区分」稳住可解释的命中率口径。详见 [竞彩预测命中率优化.md](竞彩预测命中率优化.md)#七、全量-70-很难时如何对待。

---

## 四、建议优先级（从易到难）

1. **xG 或射门/射正近似**：数据与配置已有，接入并评估对 MAE/命中率的影响，性价比高。  
2. **赛程密度 / 连续客场**：基于现有赛程即可算，与「休息天数」一起刻画疲劳与战意。  
3. **单场统计聚合为近期特征**：射门、控球等 → 风格/压制力，先做小权重或仅复盘用。  
4. **实际进球 − xG（运气/把握能力）**：在 xG 接入后顺带算，作为轻量修正或展示。  
5. **裁判、动机、阵容/身价等**：有明确产品需求或数据源后再排期。

## 五.五、为什么「预测总进球」多是 2.0～2.1？

仪表盘「预测总进球」列 = 主队期望进球 + 客队期望进球。若多数场次都显示在 **2.0、2.05、2.10、2.11** 附近，是因为：

1. **联赛平均收缩**  
   模型在「主/客队近期场次不足」时会向**联赛场均进球**收缩（见 `engine/predict.py` 中 `PREDICT_LEAGUE_SHRINKAGE_MIN_SAMPLES`，默认样本不足 5 场即收缩）。  
   联赛平均一般约 **主 1.0～1.05、客 1.0～1.05**，合计约 **2.0～2.1**，所以缺数据时预测总进球会集中在这一带。

2. **竞彩场次依赖主库历史**  
   竞彩预测时，主客队通过 `jingcai_teams` 映射到主库 `teams`，再按 `home_team_id` / `away_team_id` 在主库 `matches` 里查**该联赛、该队**的近期比分。若主库没有该联赛/球队的足够历史（例如只拉了五大联赛、或该队比赛未同步），则「近期场次」很少甚至为 0，就会触发上述收缩，得到接近 2.0～2.1 的总进球。

3. **如何让数值差异更大**  
   - **补数据**：确保主库有这些比赛所在联赛、球队的**完整历史赛程与完赛比分**。具体步骤见 **[如何补充主库数据.md](如何补充主库数据.md)**（`ingest-fd` / `ingest-api-history` 多赛季 + 竞彩队名映射 + 重新跑预测）。  
   - **体彩历史交锋**：已接入 `h2h_override`，有体彩历史交锋时会与近期期望进球融合，可在一定程度上拉开差异。  
   - **可选调参**：如增大 `PREDICT_LEAGUE_SHRINKAGE_MIN_SAMPLES`（例如 8～10），样本不足时收缩更少，数值会更分散，但噪声也会增加；根本仍是补足数据。

仪表盘上「预测总进球」列标题和单元格的 tooltip 已说明：样本不足时会向联赛平均收缩，补足主库该联赛/球队历史后差异会更大。

## 六、MongoDB 中「尚未落库」的展示用数据及获取方式

以下数据在仪表盘/接口中会用到，但当前可能显示为「暂无」，对应获取方式如下。

| 数据 | 当前来源 | 获取方式 | 说明 |
|------|----------|----------|------|
| **历史交锋** | 来自 `matches`：同一主客队 + 同赛事的历史场次 | ① 多拉几年赛程：`ingest-api-football` 拉 2022–2026 等，matches 越多 H2H 越全。<br>② 用 API-Football 的 **Head to Head** 接口补全：`fixtures/headtohead?h2h=team1_id-team2_id`，将返回的场次以 `source_id=af_{id}` 写入 `matches`，则模型与展示都会自动用上。 | 见命令 `h2h-backfill`。 |
| **休息天数** | 实时计算：该队在本场日期**之前**最近一场的日期差 | 无需单独落库。在「预测列表」接口里按场次计算 `predict_days_since_last_match(home_id, match_date)` / away，返回 `home_days_rest`、`away_days_rest`；前端展示「主队休息 N 天 / 客队休息 M 天」。 | 依赖 `matches` 中该队历史场次足够（多赛季 ingest 后即有）。 |
| **主队优势 / 客队优势** | 由**预测概率**推导：`(prob_home_win - prob_away_win) * 100` 作为优势指数 | 无需单独落库。只要该场次有 `predictions`（`prob_home_win`、`prob_away_win`），前端即可画「主客队优势趋势」条。 | 确保预测流程已跑并写入 `predictions`。 |

- **历史交锋**：要么多拉几年赛程让 matches 覆盖更多同对阵，要么用 H2H 接口把缺失的对阵历史写入 matches。
- **休息天数**：接口层按场次计算并返回即可；若 `matches` 缺历史，先补赛程再算。
- **主/客队优势**：配置项 `PREDICT_HOME_ADVANTAGE` 等只影响模型；展示上的「优势」来自预测概率，不占新字段。

## 七、球队中文名与 Web 展示（英文名/中文名）

- **teams 表**：已有字段 `name_zh`（中文名）。MongoDB 与 SQLite 均支持；新写入队伍时可通过 `ensure_team_by_id(id, name, name_zh=...)` 传入。
- **matches 表**：MongoDB 的 matches 文档会冗余主客队英文/中文名字段 `home_team_name`、`away_team_name`、`home_team_name_zh`、`away_team_name_zh`，便于列表展示与检索。新插入比赛时 `insert_match` 会从 teams 表自动带出；历史比赛可用回填命令补全。
- **Web 展示**：仪表盘列表与接口中主客队展示格式为 **英文名/中文名**（有中文时），仅无中文时显示英文名。

**维护流程：**

1. 在 **data/team_name_zh_mapping.json** 中维护「英文名 → 中文名」映射（键为 teams 表中的 `name`，值即中文名）。项目内已带示例（如 Chelsea FC → 切尔西）。
2. 执行 **`python scripts/update_team_name_zh.py`**，按映射表批量更新 MongoDB/SQLite 中 `teams.name_zh`。
3. 若使用 MongoDB，执行 **`python main.py backfill-match-names-zh`**，用 teams 的 name/name_zh 回填 matches 文档中空缺的 `home_team_name`、`away_team_name`、`home_team_name_zh`、`away_team_name_zh`。
4. 查看缺失中文名的球队：**`python scripts/list_teams_missing_name_zh.py`**，输出可继续补全到 mapping 文件后再执行步骤 2、3。

## 八、预测模型「数据还不够」时怎么做

预测模型依赖的**输入**与「数据不够」时的表现、补数顺序如下。

### 模型用到的数据与缺口表现

| 输入 | 来源 | 不够时的影响 | 如何补 |
|------|------|--------------|--------|
| **主/客近期比分** | matches（主主场、客客场最近 N 场） | 新队或新赛季场次少 → 回退到混合近期，期望进球不稳 | 多赛季 ingest，保证每队有足够历史场次 |
| **历史交锋** | matches（同主客对） | H2H 融合权重低或为 0，同对阵复用少 | `h2h-backfill`；多赛季 matches 自然增多 |
| **胜平负赔率** | match_odds | 无法与模型概率融合，仅用纯模型概率 | 见下「赔率」行；`link-match-odds` 关联到比赛 |
| **伤停** | match_injury | 缺阵不参与下调，期望进球可能偏乐观 | `injury-api` 或 `injury-api-by-db` 按日/按赛季拉 |
| **积分榜排名** | league_standings + matches.home_rank/away_rank | 排名微调不生效，势均力敌场次略逊 | `standings-api` + `standings-backfill` 回填每场排名 |
| **休息天数** | matches（赛程密度） | 疲劳系数缺，连续作战未体现 | 依赖 matches 赛程完整，多赛季 ingest 即可 |

### 推荐补数顺序（一条龙）

按下面顺序执行，可把模型能用的数据尽量补全（MongoDB 环境示例）：

1. **赛程（基础）**  
   `python main.py ingest-api-history` 或按需 `ingest-fd --seasons 2024,2025,2026`  
   → 保证 matches 里五大联赛多赛季、多场次，近期与历史交锋才有数据。

2. **积分榜**  
   `python main.py standings-api --season 2025`  
   `python main.py standings-backfill --seasons 2024,2025`  
   → 当季排名 + 回填历史场次的 home_rank/away_rank。

3. **伤停**  
   `python main.py injury-api-by-db --years 2025 --skip-existing`（或按需改年份）  
   → match_injury 有数据，预测时伤停才会参与下调。

4. **赔率（可选但建议）**  
   - 近期 7 天：`python main.py odds-api-by-db --limit 7`  
   - 体彩当天：`python main.py sporttery-odds-to-db --date $(date +%Y-%m-%d)`  
   - 若配置了第三方竞彩 API：`python main.py jc-odds-to-db --dates 2025-01-01,2025-12-31`  
   然后：`python main.py normalize-team-names` → `python main.py link-match-odds`  
   → 预测时才能做赔率与模型概率融合。

5. **历史交锋（可选）**  
   `python main.py h2h-backfill --years 2024,2025`  
   → 同主客对场次增多，H2H 融合更稳。

6. **重新预测与评估**  
   `python main.py predict-from-mongo-matches --limit 500`（或按日期 `--dates`）  
   `python main.py predict-eval`、`python main.py prediction-log recap`  
   → 用补全后的数据重新跑预测并看命中率/MAE。

补全后若仍觉得「数据不够」，再考虑文档第二节的 xG、赛程密度、裁判等进阶数据与优先级。

## 十、predictions 与 matchs/matches 表不一致

**现象**：MongoDB 里 `predictions` 的 `match_id` 与比赛表（`matches` 或你实际使用的 `matchs`）对不上——例如预测条数很多但按比赛日查不到、或评估时「有预测且已完赛」的场次为 0。

**原因说明**：

1. **比赛集合名与配置不一致**  
   项目通过 **MONGO_MATCHES_COLLECTION**（默认 `matches`）决定从哪个集合读比赛。若你的数据在集合 **matchs** 里，但未在 `.env` 中设置 `MONGO_MATCHES_COLLECTION=matchs`，则：
   - 所有「读比赛」的逻辑（含 `get_db_matches_for_date_with_scores`、`predict-from-mongo-matches`、评估用的「已完赛」列表）都会去查 **matches** 集合；
   - 若你之前用默认配置跑过预测，`predictions` 里的 `match_id` 可能来自 **matches**（或当时配置的集合），与 **matchs** 中的 `id` 不是同一批数据，就会表现为「predictions 和 matchs 对不上」。

2. **孤儿预测**  
   `predictions` 里部分 `match_id` 在当前比赛集合中不存在（例如曾切换过集合名、或比赛表被清空/重建），这些预测无法与任何一场比赛关联。

3. **重复预测**  
   同一 `match_id` 在 `predictions` 里有多条文档，评估/去重逻辑会按「每组保留一条」处理，但数量上会显得与比赛表不一致。

**处理步骤**：

1. **检查一致性**（仅 Mongo）：  
   `python main.py predict-check-consistency`  
   会输出：当前使用的比赛集合名、比赛文档数、predictions 文档数、能对上比赛的预测数、孤儿预测数量及示例 `match_id`。

2. **若比赛实际在 matchs 集合**：  
   在 `.env` 中设置 `MONGO_MATCHES_COLLECTION=matchs`，然后对 **matchs** 重新跑预测（此前基于 matches 的预测会变成「孤儿」）：  
   `python main.py predict-from-mongo-matches --limit 200`（或按需加 `--dates`）。

3. **清理孤儿预测**（可选）：  
   确认不需要保留「match_id 在比赛表中不存在」的预测后：  
   `python main.py predict-check-consistency --delete-orphans`

4. **去重**：  
   `python main.py predictions-dedup`（按 `match_id` 保留一条）。

完成后，predictions 与 matchs（或 matches）应一一对应；Web 仪表盘按比赛日筛选、以及 `predict-eval` 等评估会基于同一套比赛数据。
