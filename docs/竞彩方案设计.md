# 竞彩方案设计

本文档描述「竞彩」在足球分析项目中的定位、数据来源、MongoDB 存储设计与实现要点。当前项目阶段以 2023–2026 年五大联赛数据统计为主；竞彩采用**体彩网（场次/赛果）+ 体彩 API（固定奖金赔率）**两种来源，数据全部保留在 MongoDB，便于后续接入预测与复盘。

---

## 一、竞彩在系统中的定位

- **竞彩**：以体彩竞足彩场次与玩法（胜平负、让球胜平负、比分、总进球、半全场）为对象，提供「场次 → 赔率 → 预测 → 复盘」能力。
- **数据原则**：仅使用体彩官方渠道——① 体彩网（场次与赛果）② 体彩 API（固定奖金赔率），不依赖第三方竞彩 API；两类数据均落库 MongoDB 做长期保留与关联。
- **与现有预测的关系**：竞彩场次/赔率入库后，可与现有 `engine/predict.py`、`match_odds`、`prediction_log` 等打通；本方案先约定存储与数据流，实现时再对接预测与复盘。

---

## 二、数据来源与职责

| 数据类型             | 来源           | 说明                                   |
|----------------------|----------------|----------------------------------------|
| 竞彩场次 / 赛果      | 体彩网         | 场次列表、比赛日、主客队、联赛、全场/半场比分（开奖结果） |
| 竞彩固定奖金赔率     | 体彩 API       | 胜平负、让球胜平负、比分、总进球、半全场等官方固定奖金 |

不采用：第三方竞彩赔率 API、API-Football 赔率作为竞彩主数据（现有 match_odds 中 API-Football 仍可用于非竞彩预测，与体彩数据通过 `source` 区分）。

### 让球数数据来源说明（与官网页面的区别）

- **你看到的官网页面**：中国体彩官网 **https://www.lottery.gov.cn/jc/jsq/zqspf/**（竞彩 → 计算器 → 足球胜平负）上展示的让球数，是官方渠道的展示页，数据完整。
- **本项目当前参考的链接**：我们**没有**直接抓取 lottery.gov.cn。让球数来自 **体彩网 sporttery.cn** 的接口：
  - 场次列表：`https://webapi.sporttery.cn/gateway/uniform/fb/getMatchDataPageListV1.qry`、`https://m.sporttery.cn/api/mjc/zqsj` 等（见 `etl/sporttery_crawl.py` 的 `_try_api_fetch`）；
  - 单场固定奖金（含让球数）：`https://webapi.sporttery.cn/gateway/uniform/football/getFixedBonusV1.qry`（按体彩场次 ID 请求，解析 `value.oddsHistory.hhadList[].goalLine`）。
- **为何有时没有让球数**：体彩网接口对「当天或近期」才有数据，历史日期常返回空；列表接口有时不包含让球，需逐场调 getFixedBonusV1 补全；若某日无五大联赛或请求失败，则 match_odds 中无 `rqspf_handicap`，页面上会显示为「模型推算」的让球数（见 API/前端逻辑）。
- **若要与官网一致**：官网页 https://www.lottery.gov.cn/jc/jsq/zqspf/ 实际请求体彩同源接口（webapi.sporttery.cn），已接入：
  - **getMatchCalculatorV1.qry**（channel=c&poolCode=hhad,had）：按日拉取场次与让球/胜平负计算数据；
  - **getSupportRateV1.qry**（matchIds=…&poolCode=hhad,had&sportType=1）：按场次 ID 拉取让球与胜平负支持率。
  执行 `sporttery-odds-to-db` 时会自动用上述接口补全让球数；执行 `lottery-gov-odds-to-db` 时也会优先调上述接口（无需开浏览器）。
- **竞彩与 API 的日期对齐**：竞彩页面按「比赛编号日期」（如 260227 = 2月27日）分组，但列表内比赛可能是次日凌晨开球（如 02-28 01:30）。本系统在解析体彩时按开球时间推算**实际比赛日**（凌晨 00:00–11:59 视为次日），将 `match_odds.log_date` 与 API 的 `matches.match_date` 统一为实际比赛日，便于 `link-match-odds` 正确关联。

## 三、MongoDB 存储设计

### 3.1 竞彩场次 / 赛果：集合 `jingcai_fixtures`

- **用途**：存放体彩官方竞彩场次及开奖赛果，与现有 `matches`（API 赛程）区分。
- **数据来源**：体彩网爬虫/接口（如 `etl/sporttery_crawl.py` 的 `crawl_sporttery_for_date`、赛果接口等）。

| 字段                 | 类型     | 说明 |
|----------------------|----------|------|
| `sporttery_match_id` | string   | 体彩场次编号（如 周三007 对应编号），唯一标识体彩场次 |
| `match_date`         | string   | 比赛日 YYYY-MM-DD |
| `home_team`          | string   | 主队名（与体彩展示一致，可再做系统队名映射） |
| `away_team`          | string   | 客队名 |
| `league_cn`          | string   | 联赛中文（如 英超、西甲） |
| `home_score`         | int/null | 全场主队进球，未开赛或未知可为 null |
| `away_score`         | int/null | 全场客队进球 |
| `half_home_score`    | int/null | 半场主队进球，无则 null |
| `half_away_score`    | int/null | 半场客队进球 |
| `source`             | string   | 固定为 `"sporttery"` |
| `created_at`         | string   | ISO 时间，首次写入 |
| `updated_at`         | string   | ISO 时间，最近更新（如赛果回填时更新） |

- **唯一性**：建议以 `(match_date, sporttery_match_id)` 或 `(match_date, home_team, away_team, league_cn)` 做 upsert，避免重复。
- **赛果更新**：完赛后由体彩网赛果接口抓取比分，更新同一条文档的 `home_score`、`away_score`、半场字段及 `updated_at`。

### 3.2 竞彩固定奖金赔率：集合 `match_odds`（扩展）

- **用途**：与现有 `match_odds` 共用集合；体彩赔率用 `source = "sporttery"` 区分，并扩展体彩玩法字段。
- **数据来源**：体彩 API（如 `getFixedBonusV1.qry`），按体彩场次 ID 拉取单场固定奖金。

**现有字段（保留）**：`log_date`, `home_team`, `away_team`, `league_cn`, `spf_win`, `spf_draw`, `spf_loss`, `source`, `created_at`；可选已有 `ah_handicap`, `ah_home`, `ah_away`。

**体彩扩展字段建议**：

| 字段                 | 类型   | 说明 |
|----------------------|--------|------|
| `source`             | string | 体彩赔率固定为 `"sporttery"` |
| `sporttery_match_id` | string | 体彩场次编号，与 `jingcai_fixtures` 关联 |
| `rqspf_handicap`     | 数值   | 让球数（如 -1、0、1） |
| `rqspf_win`          | string | 让球主胜赔率 |
| `rqspf_draw`         | string | 让球平赔率 |
| `rqspf_loss`         | string | 让球客胜赔率 |
| `bf`                 | object | 比分玩法赔率（结构可按体彩 API 解析结果存） |
| `zjqs`               | object | 总进球玩法赔率 |
| `bqc`                | object | 半全场玩法赔率 |

- **唯一性**：仍按 `(log_date, home_team, away_team, league_cn)` 做 upsert；若需区分同一场多条记录，可配合 `source="sporttery"` 与 `sporttery_match_id`。
- **关联**：通过 `sporttery_match_id` 或 `log_date + home_team + away_team + league_cn` 与 `jingcai_fixtures` 对应，便于「场次 + 赔率 + 赛果」统一查询。

---

## 四、数据流与补全逻辑

1. **场次**：按日期从体彩网拉取竞彩场次 → 解析 `sporttery_match_id`、主客、联赛、比赛日 → 写入/更新 `jingcai_fixtures`（upsert）。
2. **赛果**：完赛后从体彩网拉取该日赛果 → 匹配 `jingcai_fixtures` 中对应场次（按场次编号或主客+日期）→ 更新 `home_score`、`away_score`、半场比分与 `updated_at`。
3. **赔率**：对有 `sporttery_match_id` 的场次调用体彩 API `getFixedBonusV1.qry` → 解析胜平负、让球、比分、总进球、半全场 → 写入 `match_odds`（`source="sporttery"`），并填 `sporttery_match_id` 及扩展字段。

这样实现「体彩网 + 体彩 API」结合补全竞彩数据，且全部保留在 MongoDB。

---

## 五、实现注意点

- **队名**：体彩多为中文队名；若要与现有 `teams` / `matches` 关联，可在写入前或查询时做队名规范化（如复用现有 `team_name_normalize`），并在文档中约定「竞彩集合以体彩展示名为准，关联时再映射到系统队名」。
- **幂等**：抓取脚本建议按「日期 + 体彩场次 ID」或上述唯一键做 upsert，避免重复插入；赔率同理。
- **历史**：若需 2023–2026 年竞彩数据，需确认体彩网/API 是否支持历史日期；能拉到的历史场次入 `jingcai_fixtures`，历史赔率入 `match_odds`（source=sporttery）。
- **集合与代码**：MongoDB 为无模式，`match_odds` 扩展字段可不改表结构直接加；若使用 SQLite/ORM 的 `match_odds`，需在 schema 中增加体彩相关列；建议以 MongoDB 为主时在 `db/mongo.py` 的集合列表中显式列出 `jingcai_fixtures`（若新建该集合）。

## 六、与现有能力的关系（后续扩展）

- **预测**：竞彩场次可从 `jingcai_fixtures` 读取，赔率从 `match_odds` 中 `source="sporttery"` 读取，再调用现有 `predict_match` 与赔率融合逻辑。
- **复盘**：用 `jingcai_fixtures` 的赛果与 `predictions` / `prediction_log` 对照，或把体彩赛果回填到 `prediction_log` 的 actual_* 字段，再跑现有 recap。
- **文档**：本方案与 `可补充数据与模型提升.md`、`预测流程图.md`、`项目结构.md` 并列，后续接入竞彩逻辑时以本文档为存储与数据源约定。

## 七、体彩对阵详情页与竞彩今日列表存库字段

### 对阵详情页（zqdz）与排名数据

体彩**对阵详情页**（如 [https://www.sporttery.cn/jc/zqdz/index.html?showType=2&mid=2037891](https://www.sporttery.cn/jc/zqdz/index.html?showType=2&mid=2037891)）用于获取某场比赛的对阵详情。页面上数据由后端接口动态加载，抓取时打开该页可**截获接口返回的 JSON**（如 getMatchHeadV1、getMatchFeatureV1 等），解析排名、赛季成绩、主客队简称/英文名等。展示的补充信息包括：

- **主队/客队排名**：页面模板中为 `pageTitle.wbsjStats.home.ranking`（主队排名）、`pageTitle.wbsjStats.away.ranking`（客队排名）。
- **赛季总成绩**：`wbsjStats.home` 下的 `sWinGoalMatchCnt`（胜）、`sDrawMatchCnt`（平）、`sLossGoalMatchCnt`（负）等；客队同理。
- **主/客场成绩**：主队 `sHomeWinGoalMatchCnt` 等，客队 `sAwayWinGoalMatchCnt` 等。

项目中 `etl/sporttery_crawl.py` 的 **`fetch_sporttery_match_detail(match_id)`** 会打开该详情页（`showType=1&mid=xxx`），从响应或 HTML 内嵌数据中解析 `wbsjStats`，得到 `home_ranking`、`away_ranking`、`home_season`、`away_season`、`home_home`、`away_away` 等，供单场分析或后续扩展使用。**列表接口**（如 getMatchCalculatorV1 的 subMatchList）若返回 `homeRank`/`awayRank`，也会在解析时写入每条比赛并随列表一起存库。

### 竞彩今日列表：从拉取到存库的字段（self_improvement_football.jc_matches）

数据流：**体彩 API（getMatchCalculatorV1 / getSupportRateV1 等）→ 解析为统一 match 结构 → `jc_matches_save` 写入 `self_improvement_football.jc_matches`**。每条比赛（`matches[]` 中一项）当前包含以下字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `home_cn` | string | 主队中文名（列表展示用） |
| `away_cn` | string | 客队中文名 |
| `home` | string | 主队规范化名（内部关联用） |
| `away` | string | 客队规范化名 |
| `homeTeamAbbEnName` | string/null | 主队英文简称（API 有则存） |
| `awayTeamAbbEnName` | string/null | 客队英文简称（API 有则存） |
| **`homeRank`** | int/string/null | **主队排名**（列表 API 有则存；否则可通过对阵详情页 `fetch_sporttery_match_detail` 按场次补全） |
| **`awayRank`** | int/string/null | **客队排名**（同上） |
| `home_score` | int/null | 全场主队进球（已完赛时有值） |
| `away_score` | int/null | 全场客队进球 |
| `half_home` | int/null | 半场主队进球 |
| `half_away` | int/null | 半场客队进球 |
| `league` | string | 联赛中文（如 英超、西甲） |
| `match_date` | string | 比赛日 YYYY-MM-DD |
| `match_time` | string | 开球时间 |
| `status` | string | 比赛状态描述 |
| `match_num` | string | 比赛编号（如 周三007） |
| `match_id` | int | 体彩场次 ID（与详情页 mid 一致，用于详情页请求或补全排名） |
| `odds` | object | 赔率对象，见下表 |

**`odds` 子字段：**

| 字段 | 说明 |
|------|------|
| `rqspf_handicap` | 让球数 |
| `rqspf_win` / `rqspf_draw` / `rqspf_loss` | 让球胜/平/负赔率 |
| `spf_win` / `spf_draw` / `spf_loss` | 胜平负赔率 |

文档顶层还有：`date`（日期 YYYY-MM-DD）、`source`（如 "sporttery"）、`updated_at`、`count`（场次数）。

若需在存库时带齐**主客队排名**而列表 API 未返回，可对每条比赛的 `match_id` 调用 `fetch_sporttery_match_detail(match_id)` 取得 `home_ranking`/`away_ranking`，合并为 `homeRank`/`awayRank` 后再调用 `jc_matches_save`（注意请求次数与耗时）。

## 八、体彩对阵详情页接口与接入流程

体彩对阵详情页（如 `https://www.sporttery.cn/jc/zqdz/index.html?showType=2&mid=2037827`）的数据由后端接口动态加载，**可直接 GET 请求下列 URL 获取 JSON**（base：`https://webapi.sporttery.cn/gateway/uniform/football/`），用于「比赛分析」类数据并写入 MongoDB 供模型预测使用。

### 8.1 可用接口与对应内容（含示例 URL）

| 接口 | 用途 | 示例 URL（mid=2037891） |
|------|------|--------------------------|
| **getMatchHeadV1.qry** | 对阵头部（图一：主客队名、排名、赛季总/主客场成绩） | `.../getMatchHeadV1.qry?source=web&sportteryMatchId=2037891` |
| **getInjurySuspensionV1.qry** | 主客队伤停信息 | `.../getInjurySuspensionV1.qry?sportteryMatchId=2037891` |
| **getMatchPlayerV1.qry** | 主客队射手信息（最近 N 名） | `.../getMatchPlayerV1.qry?sportteryMatchId=2037891&termLimits=3` |
| **getMatchResultV1.qry** | 主客队相同主客场的比赛结果 | `.../getMatchResultV1.qry?sportteryMatchId=2037891&termLimits=10&tournamentFlag=0&homeAwayFlag=1` |
| **getResultHistoryV1.qry** | 历史交锋：相同主客场全部赛制 | `.../getResultHistoryV1.qry?sportteryMatchId=2037891&termLimits=10&tournamentFlag=0&homeAwayFlag=1` |
| **getResultHistoryV1.qry** | 历史交锋：相同主客场相同赛制 | `.../getResultHistoryV1.qry?sportteryMatchId=2037891&termLimits=10&tournamentFlag=1&homeAwayFlag=1` |
| **getMatchFeatureV1.qry** | 特征分析（近 N 场交锋、同主客、战况、场均进/失球） | `.../getMatchFeatureV1.qry?termLimits=10&sportteryMatchId=2037891` |
| getMatchTablesV2.qry | 积分榜等 | 排名相关 |
| getFutureMatchesV1.qry | 未来赛事 | 赛程 |

代码中已封装：`fetch_sporttery_match_head_v1(mid)`、`fetch_sporttery_injury_suspension_v1(mid)`、`fetch_sporttery_match_player_v1(mid, term_limits=3)`、`fetch_sporttery_match_result_v1(mid, term_limits=10, tournament_flag=0, home_away_flag=1)`、`fetch_sporttery_result_history_v1(mid, term_limits=10, tournament_flag=0|1, home_away_flag=1)`、`fetch_sporttery_match_feature_v1(mid, term_limits=10)`。

### 8.2 请求参数规律

| 参数 | 含义 | 示例 |
|------|------|------|
| `sportteryMatchId` | 体彩场次 ID，与页面 URL 的 `mid` 一致 | `2037891` |
| `termLimits` | 取最近 N 场/条（历史、未来、球员等） | `10`、`3` |
| `tournamentFlag` | 0=全部赛制，1=相同赛制（历史交锋/比赛结果） | `0`、`1` |
| `homeAwayFlag` | 1=相同主客场（主队主场 vs 客队客场） | `1` |
| `source` | 请求来源（getMatchHeadV1 用） | `web` |
| `gmMatchId` | 在 getMatchTablesV2.qry 中使用，可与 sportteryMatchId 同值 | `2037891` |

### 8.3 返回结构（通用）

- **顶层**：`success`（布尔）、`errorCode`（"0" 表示成功）、`errorMessage`（如 "处理成功"）、`emptyFlag`、`dataFrom`。
- **业务数据**：在 `value` 中；先判断 `success === true && errorCode === "0"` 再解析 `value`。

### 8.4 getMatchFeatureV1.qry 的 value 字段含义（特征分析）

| 字段 | 含义 |
|------|------|
| `sportteryMatchId` | 体彩场次 ID |
| `matchId` | 内部比赛 ID（与体彩 ID 不同，关联时需区分） |
| `homeTeamShortName` / `awayTeamShortName` | 主/客队简称（如 马竞、布鲁日） |
| `homeTeamId` / `awayTeamId` | 主/客队内部 ID（可能为 0） |
| `sportteryHomeTeamId` / `sportteryAwayTeamId` | 体彩侧主/客队 ID |
| `uniformHomeTeamId` / `uniformAwayTeamId` | 统一队 ID（跨数据源对齐用） |
| `last` | 近 N 场（由 termLimits 决定）：主/客胜平负场次、进球比等 |
| `sameHomeAway` | 同主客交锋（主队主场 vs 客队客场）的胜平负等 |
| `eachHomeAway` | 各自主客场战绩（如客队客场胜平负） |
| `eachSameHomeAway` | 各自主客场的「同主客」统计 |
| `goalAvg` | 场均进球（如 homeGoalAvgCnt、awayGoalAvgCnt 及占比 Ratio） |
| `lossGoalAvg` | 场均失球（如 awayLossGoalAvgCnt、awayLossGoalAvgCntRatio 等） |

对应页上的「近5场交锋」「同主客交锋」「近10场战况」「场均进球/失球」等均来自上述字段。

### 8.5 自动调用接口、解析、落库与供模型使用的流程

1. **场次与 mid 对应**  
   竞彩场次列表（体彩网/体彩 API 或 `jingcai_fixtures`）中保留体彩场次 ID（`mid` / `sporttery_match_id`），作为请求对阵详情接口的入参。

2. **按 mid 自动调用接口**  
   - 对每个需要「比赛分析」的场次，用其 `sporttery_match_id` 依次请求：`getMatchHeadV1.qry`、`getMatchFeatureV1.qry`、`getResultHistoryV1.qry`、`getInjurySuspensionV1.qry` 等（可选：`getMatchTablesV2.qry`、`getMatchResultV1.qry`、`getFutureMatchesV1.qry`、`getMatchPlayerV1.qry`）。  
   - 请求方式一般为 GET；如需 Cookie/Referer，从浏览器相同请求的 Headers 复制即可。  
   - 规律：同一页面仅 `sportteryMatchId` 随场次变化，其它参数可固定或配置。

3. **解析 JSON 并整理**  
   - 校验 `success && errorCode === "0"`，再读取各接口返回的 `value`。  
   - 将各接口的 `value` 整理成统一文档结构（见下），便于落库与模型使用。

4. **写入 MongoDB**  
   - 建议使用单独集合 **`jingcai_match_analysis`**，每条文档对应一场的「分析数据」。  
   - 文档建议字段：`sporttery_match_id`（= mid）、`match_date`、`home_team`、`away_team`、`league_cn`（可从 getMatchHeadV1 或场次列表带出）、`feature`（存 getMatchFeatureV1 的 value 或所需子集）、`result_history`（getResultHistoryV1 的列表）、`injury_suspension`（getInjurySuspensionV1）、`match_head`、`match_tables`、`future_matches`、`match_player` 等按需、`updated_at`。  
   - 以 `sporttery_match_id` 为唯一键做 **upsert**，同一场多次抓取只更新不重复插入。

5. **供模型分析预测**  
   - 预测时根据本场是否为竞彩场次（有 `jingcai_fixtures` 或 mid），从 `jingcai_match_analysis` 用 `sporttery_match_id` 读取该场分析文档。  
   - 将 `feature` 中的近 N 场胜平负、场均进/失球等转为现有 `predict_match` 可用的输入（如补充或替代「近期场均」、历史交锋等），再调用现有预测逻辑；或先仅落库与展示，预测仍用现有逻辑，待数据稳定后再接入模型。

6. **幂等与频率**  
   - 同一 `sporttery_match_id` 可多次拉取（如赛前更新伤停、特征）；按 `sporttery_match_id` 做 upsert 即可。  
   - 请求频率需控制，避免对体彩接口造成压力。

### 8.6 与第三节、第四节的关系

- **场次/赛果**（第三节 `jingcai_fixtures`）、**固定奖金**（第三节 `match_odds`）仍按体彩网/体彩 API 的列表与固定奖金接口获取。  
- 本节接口用于**单场对阵详情与比赛分析**，在已有场次（含 `sporttery_match_id`）基础上按需拉取并落库至 `jingcai_match_analysis`，作为竞彩维度的补充数据源，供模型分析预测使用。

## 九、历史与未来数据边界（竞彩 + 赛程）

当前**历史数据**已完善到 **2026-02-23**；**2026-02-24 及以后**的「未来」日期在 DB 中暂无赛程或竞彩场次时，可按下列方式补充。

### 8.1 现状说明

| 数据类型 | 历史（≤ 2026-02-23） | 未来（≥ 2026-02-24） |
|----------|----------------------|----------------------|
| **matches（赛程/赛果）** | 已由 `ingest-api-history` / `ingest-fd` 等写入 | 当前 ingest 仅拉**已完赛**场次，未开赛不会入库，故「未来日期」在 matches 中为空 |
| **竞彩场次 / 赔率** | 体彩按日拉取或历史接口（若支持）可落库 `jingcai_fixtures`、`match_odds` | 体彩网/体彩 API 通常只对**当天或近期**有数据，无法一次性拉「整月未来」 |

因此：**竞彩方案可以照常加入**；历史部分直接复用现有数据；**未来部分**需要靠「按日/按周拉取」或「扩展 ingest 拉未开赛场次」来补齐。

### 8.2 未来数据怎么弄

**方案 A：赛程（matches）——拉取未开赛场次入库**

- **推荐**：扩展 API-Football 的赛程拉取，除已完赛外也写入**未开赛**（status 为 NS、TBD、TIMED 等）场次。  
  - 在 `etl/api_football_match_ingest.py` 中增加「按 league+season 拉全量 fixtures、不筛 FT」的逻辑（或新增命令如 `ingest-api-upcoming`），将未开赛的场次 upsert 到 MongoDB `matches`，`home_score`/`away_score` 置为 null。  
  - 这样 2026-02-24 之后的比赛日一旦被 API 公布，下次执行拉取后就会有对应记录，预测列表、竞彩关联都可基于同一套 matches。
- **备选**：若主要用 football-data.org，其 `ingest-fd` 已会写入未开赛（SCHEDULED/TIMED）；若当前生产数据以 API-Football 为主，可定期再跑 `ingest-fd` 仅拉当季，把未开赛写入后与现有 matches 按 source_id/日期合并（需在 repo 层支持多源 match 合并或统一用 FD 作未来赛程来源）。

**方案 B：竞彩场次与赔率（未来几天）**

- **按日拉取**：体彩网/体彩 API 对「未来」只暴露近期（如当天、明天、后天）。  
  - 每天定时跑一次：`python main.py sporttery-odds-to-db --date $(date +%Y-%m-%d)`（或 `--days 3` 拉最近 3 天）。  
  - 场次写入 `jingcai_fixtures`（若已实现 MongoDB 集合）或现有 `sporttery-odds-to-db` 所写的 `match_odds`（source=sporttery）；赔率同时落库。  
  - 这样「未来」会随日期推进自然积累，无需一次性拉整月。
- **体彩对阵详情（可选）**：对已出现在 `jingcai_fixtures` 中的未来场次，用第七节的 `getMatchFeatureV1.qry`、`getFutureMatchesV1.qry` 等按 `sporttery_match_id` 拉取，写入 `jingcai_match_analysis`，供预测或展示用。

**方案 C：预测列表与前端展示**

- 若某日 DB 中**没有** matches 记录：  
  - **仅竞彩**：可只展示「来自 jingcai_fixtures / 体彩按日拉取」的场次，并标注「仅竞彩场次，无 DB 赛程」。  
  - **要同时展示五大联赛赛程**：必须先有未来赛程入库（方案 A），否则该日期列表为空；可前端提示「该日期暂无赛程，请稍后重试或运行 ingest-api-upcoming / ingest-fd」。

### 8.3 建议落地顺序

1. **先接入竞彩方案**：历史数据到 2026-02-23 已具备，竞彩存储（`jingcai_fixtures`、`match_odds` 体彩扩展、`jingcai_match_analysis`）与现有预测/复盘逻辑按文档第三、四、七节实现即可。  
2. **未来赛程**：实现方案 A 之一（API-Football 拉未开赛 或 football-data 补未来），使 2026-02-24 之后的比赛日有 matches 记录。  
3. **未来竞彩**：每日定时跑 `sporttery-odds-to-db --date 当天`（及可选 `--days 2`），使竞彩场次与赔率覆盖「今天与明后天」。  
4. **前端/接口**：按「有 matches 用 matches，无则用 jingcai_fixtures」的策略展示列表，并区分「历史 / 未来」与数据来源提示。

按以上方式，历史沿用现有数据，未来通过「未开赛 ingest + 体彩按日拉」即可逐步补齐，竞彩方案可完整加入。
