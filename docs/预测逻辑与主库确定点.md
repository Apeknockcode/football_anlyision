# 预测逻辑与主库确定点

本文档明确「主库为 self_improvement_football」时的数据流、预测逻辑入口，以及 football 库的可利用方式，便于提高模型命中率时做统一约束。

---

## 1. 主库与配置（确定点）

- **主库**：业务默认主库为 **`self_improvement_football`**。
- **配置方式**：在 `.env` 中设置：
  - `MONGO_DB_NAME=self_improvement_football`
  - `MONGO_SELF_IMPROVEMENT_DB_NAME=self_improvement_football`（与主库一致时，竞彩与通用数据同库）
- **代码约定**：
  - `db.repo` 通过 `db.mongo.get_mongo_db()` 读写，使用的库名 = `config.MONGO_DB_NAME`。
  - 因此当 `MONGO_DB_NAME=self_improvement_football` 时，**所有**通过 repo 访问的集合（matches、teams、competitions、predictions、prediction_log、match_odds、match_injury、league_standings 等）均落在 **self_improvement_football**。
  - 竞彩专用逻辑通过 `db.self_improvement.get_self_improvement_db()` 访问，库名 = `config.MONGO_SELF_IMPROVEMENT_DB_NAME`，通常与主库同名。

**结论**：主库 = self_improvement_football 时，预测所需的结构化数据（比赛、球队、赛事、赔率、伤停、积分榜、预测记录）都应来自或写入 **self_improvement_football**，不再依赖 football 库作为主数据源。

---

## 2. 预测数据流（确定点）

| 环节 | 数据来源 | 说明 |
|------|----------|------|
| 赛程输入 | `self_improvement_football.jingcai_match_analysis` | 按 `jc_date` 列出待预测场次；主客、联赛、`match_id`、`api_football_fixture_id` 等 |
| 球队/赛事解析 | 主库（repo）`teams` / `competitions` | `resolve_team_by_name`、`resolve_competition_by_name`、`ensure_team_by_name`、`ensure_competition_by_name` 均走 repo → 主库 |
| 历史比赛（近期形式、联赛场均、H2H） | 主库（repo）`matches` | `predict_team_recent_form*`、`predict_league_avg_goals`、`predict_head_to_head` 等均查主库 matches |
| 赔率 | 主库 `match_odds` + 可选 `jingcai_match_analysis` 内嵌 | 优先 `match_odds_load_by_match_id(match_id)`；竞彩单场可从 analysis 的 `odds` 或解析结果取 |
| 伤停 | 主库 `match_injury` + `jingcai_match_analysis` 解析 | `load_injury_from_db()` 读主库；单场可从 `parse_jingcai_analysis_for_predict` 得到 home_absent/away_absent 等 |
| 积分榜/排名 | 主库 `league_standings` + API-Football standings | `standings_get_for_match` 等；缺省时可用 api_football_standings 按联赛+赛季补 |
| xG/单场统计 | `self_improvement_football.api_football_statistics` 等 | 通过 `parse_jingcai_analysis_for_predict` 或 `_load_odds_injury_rank_for_match` 传入 predict |
| 预测结果写入 | `self_improvement_football.jc_predictions` | 竞彩预测；通用预测可写主库 `predictions` / `prediction_log`（主库即 self_improvement_football） |

**结论**：提高命中率时，所有「可调」的预测输入（历史比赛、赔率、伤停、积分榜、xG）都应优先保证来自 **self_improvement_football**（主库 + 同库下的 jingcai_* / api_football_* 集合）。

---

## 3. football 库的定位与可用数据（确定点）

- **定位**：football 为**旧库/历史库**，之前未完善的数据仍可能在其中；当前项目**不**默认从 football 读任何数据。
- **主库 = self_improvement_football 时**：repo 只读主库，**不会**自动读 football。若希望利用 football 的数据，只能通过以下两种方式之一：
  1. **迁移/同步**（推荐）：把 football 中有价值的数据（如历史 matches、match_odds、league_standings、teams、competitions）同步或迁移到 self_improvement_football，之后预测逻辑无需改代码，自然用主库数据。
  2. **显式 Fallback**：在需要「历史比赛更多」的场景（如近期形式、联赛场均、H2H），在 repo 或 engine 中增加「主库无或不足时从 football 读」的逻辑（需按集合、按查询封装，避免散落）。

**football 中可能对预测有用的集合**（与 repo/mongo 中主库集合对应）：

| 集合 | 用途 | 建议 |
|------|------|------|
| `matches` | 近期形式、联赛场均、H2H | 若主库场次不足，可迁移到主库或做 fallback 读 |
| `teams` / `competitions` | 球队/赛事解析、name_zh | 建议迁移到主库，保证主库解析完整 |
| `match_odds` | 赔率融合 | 可迁移到主库或 fallback |
| `league_standings` | 排名微调 | 可迁移或 fallback |
| `match_injury` | 伤停 | 若主库缺历史，可迁移或 fallback |
| `predictions` / `prediction_log` | 评估/校准 | 若需用旧预测做评估，可迁移或只读 fallback |

**结论**：能用的就迁移到 self_improvement_football 用；不能迁移的再考虑在个别读路径上对 football 做 fallback，并明确写在文档与代码注释中。

### 迁移与删除 football 的操作步骤

1. **迁移数据**（只追加，不覆盖目标库已有文档）：
   ```bash
   python main.py migrate-football-to-self-improvement
   ```
   可选 `--dry-run` 先查看会迁移哪些集合及条数。

2. **确认无误后删除 football 库**（不可恢复）：
   ```bash
   python main.py migrate-football-to-self-improvement --drop-source-db --yes
   ```

3. **后续只使用 self_improvement_football**：在 `.env` 中设置：
   - `MONGO_DB_NAME=self_improvement_football`
   - `MONGO_SELF_IMPROVEMENT_DB_NAME=self_improvement_football`

## 4. 预测逻辑入口与命中率相关（确定点）

- **竞彩单场预测**：`main._predict_one_jc_match`  
  - 输入：`jingcai_match_analysis` 的一条 + `jc_date`。  
  - 内部：解析主客队与赛事（主库）→ 拉取赔率/伤停/排名/xG 等（主库 + jingcai 解析）→ `engine.predict.predict_match` → 可选 API 预测融合 → 写 `jc_predictions`。
- **批量竞彩预测**：`predict_jc_from_self_improvement`（按 jc_date / 年 / 日期区间），循环调用 `_predict_one_jc_match`。
- **复盘与评估**：`repredict_jc_evaluable_matches` 对已完赛的 jingcai 场次重算预测并写回 `jc_predictions`；评估/校准使用主库的 `prediction_log`、`predictions` 与 `jc_predictions`。

**与命中率直接相关的配置/数据**（均在 config 或 data 文件中）：

- 赔率融合：`PREDICT_ODDS_FUSION_WEIGHT_MODEL`、`PREDICT_USE_ODDS_FUSION`
- API 预测融合：`PREDICT_USE_API_PREDICTIONS`、`PREDICT_API_PREDICTIONS_WEIGHT`
- 校准：`PREDICT_USE_CALIBRATION`、`PREDICT_CALIBRATION_PATH`
- ML 修正层：`PREDICT_USE_OUTCOME_ML`、`PREDICT_OUTCOME_ML_WEIGHT`、`PREDICT_OUTCOME_ML_PATH`
- 单场推荐阈值：`SINGLE_REC_MIN_PROB`、`SINGLE_REC_RQ_MIN_PROB`、`SINGLE_REC_RQ_MIN_PROB_LET_FU` 等
- 细分/联赛命中率：`JC_REC_USE_SEGMENT_STATS`、`JC_REC_SEGMENT_STATS_PATH`、`JC_REC_LEAGUE_PARAMS_PATH`、`JC_REC_FOR_2026_USE_AUXILIARY` 等

**结论**：提高命中率时，在「主库 = self_improvement_football、数据源以主库为准」的前提下，优先做：  
1）数据补全（历史比赛/赔率/伤停/排名尽量进主库）；  
2）上述配置与 data 文件的调参与细分策略；  
3）必要时再考虑从 football 做有范围的 fallback 或一次性迁移。

---

## 5. 小结：需要你确认的几点

1. **主库固定**：是否确认生产/复盘环境一律使用 `MONGO_DB_NAME=self_improvement_football`（且与 `MONGO_SELF_IMPROVEMENT_DB_NAME` 一致）？  
2. **football 使用策略**：是优先「把 football 中有用的表迁移到 self_improvement_football」还是「在部分读路径保留对 football 的 fallback」？  
3. **命中率优先级**：当前更关注「单场推荐命中率」还是「全量胜平负命中率」或「让球命中率」？以便在单场阈值、细分参数、联赛 min_prob 上做针对性调整。

以上确定点可作为后续改预测逻辑、加 fallback 或做数据迁移的统一约束。
